# AGENTS.md — Local LLM Lifecycle Proxy

## 1. Назначение

Разработать локальный Python-сервис **LLM Lifecycle Proxy** для macOS Apple Silicon. Сервис предоставляет единый OpenAI-совместимый HTTP API для нескольких локальных моделей, запускаемых через `llama-server` (llama.cpp), и автоматически выгружает неиспользуемые модели из памяти. Open WebUI, Goose, MCP-клиенты и другие OpenAI-совместимые приложения должны работать с ним без знания внутреннего устройства.

Этот файл — технический контракт для AI-агентов, работающих над репозиторием. При конфликте реализации и требований ниже приоритет имеют требования. Не добавлять функции, которые нарушают обратную совместимость API, без явного решения.

## 2. Границы проекта

**Входит:** реестр GGUF-моделей, единый OpenAI API, запуск и остановка отдельных `llama-server`, маршрутизация, потоковая передача ответов, таймер простоя, ручная выгрузка, управление конкуренцией, диагностика, конфигурация YAML, безопасная работа с процессами.

**Не входит в первую реализацию:** самостоятельный inference на Python, изменение весов GGUF, скачивание моделей, встроенный RAG, UI, Docker, Redis, Celery, управление системным сервисом Ollama, кластеризация. Ollama продолжает подключаться к Open WebUI отдельно. Архитектура допускает будущие backend-адаптеры Ollama и MLX, но их не следует реализовывать заранее.

## 3. Среда и ограничения

- macOS / Apple Silicon (целевой пример: M4 Pro, 48 ГБ Unified Memory).
- Python 3.11+, `uv`, FastAPI, Uvicorn, httpx, Pydantic v2, PyYAML.
- Установленный `llama-server` из актуального llama.cpp с Metal backend.
- Веса GGUF могут находиться в `~/.ollama/models/blobs/sha256-*`; **читать напрямую**, не копировать, не перемещать, не удалять и не изменять файлы Ollama.
- Proxy слушает `127.0.0.1:11436`, внутренний llama-server — выделенный локальный порт (например, `11437`). Порты конфигурируемы; избегать `11434` (Ollama), `11435` (существующий reranker), `3000` (Open WebUI).
- По умолчанию не более одной тяжёлой модели одновременно; сервер proxy остаётся запущенным при выгруженных моделях.
- Развёртывание через user LaunchAgent возможно, но сам proxy **не должен** требовать root.

## 4. Архитектура

```text
Open WebUI / Goose / MCP / curl
             |
             v
      FastAPI Gateway (:11436)
        |             |
        |             +--> Management API (/management/...)
        v
    Model Router ---> Model Registry (models.yaml)
        |
        v
    Request Scheduler / Lifecycle Manager
        |                     |
        v                     v
    Resource Manager      Process Supervisor
                              |
                              v
                      llama-server (:11437+)
                              |
                              v
                      GGUF + Metal GPU
```

Слои должны быть разделены: API не управляет `subprocess` напрямую; backend не принимает решения о вытеснении; scheduler не знает деталей HTTP-протокола inference.

## 5. Реестр моделей

Модели описываются декларативно. Каждая имеет стабильный внешний `id`, backend, путь к весам и параметры runtime. Проверять существование GGUF, допустимость портов, уникальность ID и корректность значений при старте proxy. Не загружать веса для формирования списка моделей.

```yaml
server:
  host: 127.0.0.1
  port: 11436
  api_key_env: LLM_PROXY_API_KEY
  idle_timeout_seconds: 60
  startup_timeout_seconds: 180
  shutdown_grace_seconds: 10

resources:
  max_loaded_models: 1
  memory_budget_gib: 36
  eviction_policy: lru
  queue_timeout_seconds: 240

backend:
  llama_server_binary: /opt/homebrew/bin/llama-server
  bind_host: 127.0.0.1
  first_port: 11437

models:
  nemotron-3.5-bolt:
    backend: llamacpp
    gguf_path: /Users/sky/.ollama/models/blobs/sha256-91d63363e782c8a3d5f4be42816eba8e0d42dd2530bd07a7d0d2dc440599af75
    context_size: 8192
    gpu_layers: 99
    parallel: 1
    idle_timeout_seconds: 60
    # mmproj_path: /absolute/path/to/vision-projector.gguf
  example-model:
    backend: llamacpp
    gguf_path: /absolute/path/to/model.gguf
    context_size: 8192
    gpu_layers: 99
    parallel: 1
```

Значения памяти являются **бюджетом планировщика**, а не обещанием точного потребления. При необходимости добавить настраиваемую оценку памяти модели и запас для KV-cache и macOS. Не определять размер модели только по имени файла. Отсутствующий `mmproj_path` не должен ломать текстовую генерацию.

## 6. Публичный API

### OpenAI-совместимый интерфейс

- `GET /v1/models` — полный зарегистрированный каталог без запуска моделей.
- `POST /v1/chat/completions` — обязательный маршрут; поддерживать `stream: true/false`.
- `POST /v1/completions` — поддерживать при наличии реализации в выбранном llama-server.
- Остальные маршруты (`embeddings`, multimodal и т. д.) добавлять только после тестов поддержки backend; не рекламировать несуществующие возможности.
- Модель выбирается по полю `model`, неизвестная модель даёт корректный `404`-совместимый OpenAI error JSON.
- При переадресации подменять внешний ID на backend alias при необходимости, а во внешних ответах сохранять ожидаемый ID.
- Не удалять и не переписывать без необходимости поля `tools`, `tool_choice`, `response_format`, `reasoning`, мультимодальные части сообщений и иные параметры, поддерживаемые backend.
- SSE передавать инкрементально, без накопления всего ответа в памяти; сохранять порядок, границы событий и завершающий `[DONE]`.
- Ошибки upstream, отмены клиентов и таймауты обрабатывать без утечек слотов и процессов.

### Управление (отдельно от OpenAI API)

- `GET /management/models` — состояния, время последнего использования, активные запросы, PID, порт и причина ошибки.
- `GET /management/models/{id}` — состояние одной модели.
- `POST /management/models/{id}/load` — предзагрузка.
- `POST /management/models/{id}/eject` — выгрузка; если есть активные запросы, вернуть `409 Conflict` (по умолчанию без принудительного прерывания).
- `POST /management/models/eject-all` — выгрузить все свободные модели; занятые не прерывать.
- `GET /health` — жив ли proxy, не запускать модель.
- `GET /ready` — готов ли proxy принимать запросы; не требовать загруженных моделей.

**Не предполагать, что Open WebUI автоматически отправляет `eject`** через OpenAI API. Ручная кнопка выгрузки в Open WebUI потребует подтверждённого механизма интеграции, плагина либо отдельного UI. API выгрузки должен работать независимо от этой интеграции.

## 7. Жизненный цикл и планировщик

Состояния: `STOPPED -> STARTING -> READY -> BUSY -> READY -> UNLOADING -> STOPPED`; аварийный переход в `FAILED` из рабочих состояний. Хранить состояние, PID, число активных запросов, timestamps и ошибку. Не считать HTTP `/health` достаточным признаком готовности без проверки живого процесса и готовности модели.

1. При запросе найти модель и зарезервировать слот через scheduler.
2. Если модель уже `STARTING`, другие запросы **ожидают ту же задачу запуска**, не создавая новые процессы.
3. При лимите `max_loaded_models` вытеснить свободную LRU-модель; занятую не останавливать. Если все заняты — ожидать с ограниченным таймаутом либо возвращать контролируемую ошибку перегрузки.
4. Запустить `llama-server` через `asyncio.create_subprocess_exec` с массивом аргументов, **без shell=True**; использовать отдельный порт и уникальный alias.
5. Ожидать готовности до `startup_timeout_seconds`; при сбое собрать диагностические логи, завершить процесс, снять резервацию и сообщить понятную ошибку.
6. Передать запрос и удерживать счётчик активных запросов до окончания ответа **включая последний SSE chunk** или отмену клиента.
7. Отсчитывать `idle_timeout_seconds` от завершения последнего активного запроса. Новый запрос отменяет запланированную выгрузку.
8. При таймауте повторно проверить состояние и счётчик активных запросов под блокировкой; только затем выгрузить.
9. Завершать через `SIGTERM`, ждать grace period, затем при необходимости `SIGKILL`; дождаться освобождения порта и завершения процесса.
10. После падения процесса перейти в `FAILED`/`STOPPED` с явным статусом; разрешить ограниченные повторные попытки с backoff, исключить бесконечный restart loop.

Использовать `asyncio.Lock`/`Condition` для атомарных переходов. **Нельзя** держать глобальную блокировку во время inference или чтения SSE. Разделить короткие операции управления состоянием и длительные сетевые операции. Предусмотреть race между idle timer, eject, запуском и новым запросом.

## 8. Управление памятью

- Начальный режим — одна тяжёлая модель одновременно.
- При переключении моделей выгружать предыдущую только после завершения её активных запросов.
- Оценивать потребление весов + KV-cache + overhead; оставлять запас ОС. `memory_budget_gib` — настраиваемый лимит, не точный измеритель GPU working set.
- Не выгружать сторонние процессы Ollama, Qdrant, Docling или reranker.
- По умолчанию не запускать одновременно несколько тяжёлых `llama-server` при 48 ГБ Unified Memory.
- Собирать показатели времени холодного запуска, генерации, простоя и выгрузки. Метрики скорости токенов сохранять только если их сообщает backend.

## 9. Безопасность и эксплуатация

- Слушать только loopback по умолчанию; внешний bind — исключительно явная настройка.
- API-ключ брать из переменной окружения, не хранить секреты в `models.yaml` или Git.
- Для management API применять авторизацию не слабее публичного API; при расширении сетевого доступа предусмотреть отдельный admin token.
- Не принимать произвольные пути к файлам, аргументы процесса и команды запуска из пользовательского HTTP-запроса.
- Не логировать API-ключи, полный текст промптов и содержимое файлов по умолчанию.
- Логи — структурированные, с `request_id`, `model_id`, `pid`, переходами состояний, таймингами и диагностикой subprocess.
- Корректно закрывать `httpx.AsyncClient`, subprocess и фоновые задачи при shutdown.
- Один управляющий процесс proxy: не запускать Uvicorn с несколькими workers, пока state/scheduler хранятся в памяти процесса.
- Не запускать одновременно два proxy с одинаковым реестром и диапазоном backend-портов.

## 10. Требования к коду и тестированию

- Типизация Python, Pydantic-модели конфигурации, небольшие модули, явные исключения.
- Async для I/O, без блокирующих `subprocess.run` в обработчиках.
- Тесты с поддельным llama-server, без загрузки 21-ГБ модели в CI.
- Обязательные сценарии: пустой каталог; неизвестная модель; холодный старт; два одновременных запроса к одной модели; переключение между моделями; `stream` и `non-stream`; отмена SSE; `eject` при BUSY; idle timeout; ошибка старта; аварийное завершение процесса; очередь при лимите памяти; очистка после shutdown.
- Интеграционный тест на реальном macOS Metal backend — отдельно, opt-in.
- При тестировании проверять, что `GET /v1/models` не загружает GGUF и что после 60 секунд без активных запросов `llama-server` действительно завершён.
- Документировать команды `uv sync`, запуск proxy, curl-тесты, подключение Open WebUI, LaunchAgent и диагностику.

## 11. Порядок реализации для агентов

1. Сначала контракты конфигурации, реестр и тесты валидации.
2. Затем supervisor и state machine с тестами гонок.
3. Затем scheduler, очередь и политика LRU.
4. Затем OpenAI gateway и корректный SSE proxy.
5. Затем management API, idle eject, метрики и shutdown.
6. Затем интеграционные тесты с установленным llama.cpp и документация LaunchAgent.

Перед изменениями изучать существующий код и тесты; не переписывать работающие компоненты без необходимости. После каждого изменения запускать подходящие тесты. Если поведение llama.cpp или Open WebUI зависит от версии, проверять фактический API и флаги установленной сборки; не выдавать предположения за подтверждённую совместимость.

## 12. Критерии приёмки

1. Open WebUI видит все зарегистрированные модели через один URL даже при нуле запущенных `llama-server`.
2. Первый запрос к модели запускает ровно один процесс и возвращает ответ OpenAI API.
3. Потоковая генерация не обрывается из-за idle timeout.
4. Через 60 секунд после завершения последнего запроса модель выгружается и память освобождается ОС.
5. `eject` выгружает свободную модель, но не прерывает занятую.
6. При переключении моделей соблюдается лимит одновременных процессов.
7. GGUF из каталога Ollama используется на месте, без повторного скачивания и копирования.
8. Падение backend не приводит к зависанию proxy, вечной блокировке или утечке слотов.
9. Ollama, Open WebUI, Qdrant, Docling и другие локальные сервисы продолжают работать независимо.
10. Проект запускается на macOS через `uv`, а автозапуск через LaunchAgent описан и проверяем.
